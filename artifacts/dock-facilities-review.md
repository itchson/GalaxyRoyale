# Haven facility interaction handoff

Four original authored pixel-quad buildings are now rendered around Haven: coral upgrade fabricator, cyan shuttle hangar, green archive terminal, and gold campaign observatory/pennant. Each has a subdued shared physical pad; their authored building cells and silhouettes are distinct. They use cached object-local `PixelBody` cells and eight bounded world transforms, with no textures, new assets/dependencies, ECS bodies, physics or save state. This is authored ASCII pixel art, not an AI-image generation claim.

`Game::dock_facility_at(world: [f32; 2]) -> Option<u8>` returns IDs 0 upgrades, 1 hangar, 2 journal, 3 campaign. World centers are respectively `[-120,-80]`, `[120,-80]`, `[-120,95]`, `[120,95]`. It rejects nonfinite coordinates and requires the actual player's position inside Haven's 240-world-unit safe radius. Each facility's hit circle is radius 24; all authored building/pad corners lie inside it. Remote safe sites do not grant access to these home facilities. The method reads state without changing progression.

The minimal `lib.rs` additions declare the module, expose that method, and extract the facilities after the home station/ring, using the interpolated unshaken render camera, actual world viewport and existing frozen `cosmetic_time()`. Whole-object culling uses the verified 24-unit bound. Pads have lighting response .35 and buildings .75, both emission zero. The accent cells pulse by at most six percent; Reduced Motion forwards constant time zero. Reduced Cosmetics never removes an interactive facility.

Source-derived occupied counts: shared pad 91, upgrade building 210, hangar 257, journal 226, campaign 190. The actual native extraction test validates its pixel total against the live cached counts: **1,247 submitted quads / eight object transforms** when all four are visible. No frame-rate, browser legibility or physical phone claim is inferred from these counts.

`FlightInput` now accepts trailing `onInteract(world: [number,number]) => boolean = () => false`, after its existing optional `onFireStart`. Only initial left canvas presses and initial canvas touches invoke the callback. A consumed left press creates no capture or course and its later drag remains blocked until left release; a release outside the canvas also clears this block. An interaction callback may synchronously disable/reset input without restoring held state. Declined mouse presses navigate normally, held dragging never invokes facilities, and declined canvas touches remain joystick-only. Right mouse aim/fire and the touch fire button never invoke `onInteract`; existing optional fire-start compatibility remains for callers/tests. Root owns the menu-opening callback and no longer passes a weapon-to-menu callback.
