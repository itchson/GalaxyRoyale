The author's prepare/provenance patch is excluded from independent acceptance here. Production controller/transport/store/storage sources were read only as contracts.

No source sequencing blocker found for the default two-client Connect with responsive foreground clients. `controller.join` returns after the real service grant, before approval or RTC readiness. The service long poll wakes on queued join requests rather than consuming its entire 20-second wait. Root then polls actual approval state, verifies isolation, resolves the exact request, and waits for a new native complete commit. This is source/function review, not a live Connect pass or a timing guarantee.

## What the new gate establishes

- `client.js:211` creates a real `RTCPeerConnection`, then increments the cumulative created counter; it does not increment a declared/inferred peer value. `approval-state` (`:615`) returns current controller awaiting/request/transport/admission values and this counter. Controller state derives ready/admitted counts from actual transport peers. Root records both counters after host creation and before guest join, so rejoin does not incorrectly demand zero lifetime creations.
- `approvePendingJoin` (`wasm-review.js:283`) waits for one host pending request and guest awaiting approval, then requires unchanged created counts and zero ready/admitted peer counts before sending acceptance. Host's own native begin is expected and is not counted as a peer admission. The observation is a real snapshot/cumulative-counter gate; it does not independently observe every native begin/end operation or exact local-world internals.
- `approve-next` (`client.js:625`) requires host role and exactly one current request, and passes `requests[0].id` to the real controller. Runtime `JoinRequest` uses `id`, and transport rechecks current request membership before sending `/v1/approval`. Expired request races fail rather than approving a replacement implicitly.
- Loaded initialization (`client.js:473`) skips explicit `SaveStore.save` and `flush`. The adjusted actual-function initializer test checks both absences for the loaded case and both presences for a fresh fixture, plus real initialization ordering. It uses declared API fixtures, not an actual IndexedDB/native result.
- Launch (`server.mjs:320–343`) compares original/current Git metadata, build stamp, compiled revision and compiled Git map before constructing the service. It calls the actual service verifier and requires both pinned service paths to agree with ordinary inputs. The existing input SHA loop still verifies the actual Root service sources, with owned adapters resolved separately. Origin policy is unchanged. The new check name is allowed in strict report validation.

## Concrete limits and defects

1. **Loaded profile initialization is not a strict read-only store operation.** `SaveStore.open` opens database version 5 and a readwrite transaction (`storage.ts:826,845`), then writes normalized current/previous records when migration is needed (`:863–864`). The helper invokes open during initialization/baseline and verify. Skipping explicit save/flush preserves this narrower guarantee, but cannot establish zero persistent writes for legacy or noncanonical records. Root was notified before live staging. A strict existing-save preservation case requires a genuinely read-only observation path or an explicitly scoped current-schema QA origin; no existing profile was opened or mutated by this review.
2. **The 15-second approval polling deadline is not a hard wall-clock bound.** Each awaited child reply has the existing 75-second command timeout. `approvePendingJoin` checks its deadline after both replies and breaks on observed pending state before checking time. Responsive foreground clients normally resolve immediately and are compatible with the service's 20-second pending window, but a stalled child can overrun it. The actual service rejects an expired request; Root must retain failures rather than calling this a 15-second measured pass. The 180-second default client lifetime also remains finite.
3. **Child approval errors retain only a generic controlled reason.** `approval_not_pending` is in the parent's action-display allowlist, but the child event handler (`client.js:724`) maps it through fifth-only failure reasons to `native_action_failed`; the parent reply filter also uses the narrower `failureCodes`. The direct `command` test sees the precise thrown code, while the real message route does not. This does not permit a false success or expose a capability, but detailed negative-case reporting is still incomplete.

The first approval gate is appropriate for the currently supported default helper flow. Decline, code replacement/lock, failed connection, exact local-world restoration, raw persisted baseline preservation and the shipped panel/Main save-entry UX remain separate unperformed live gates in the parent plan.
