## Supported source explanation

1. A valid public `diagnostic("warp x y")`, including `warp 0 0`, resets the run and then sets both `boss_qa_scene` and `diagnostic_scene` true before moving the player (`lib.rs:3894–3904`). Merely returning to Haven does not clear isolation. Explicit `diagnostic("home"|"dock")` calls `reset_to_dock`; reset clears these flags (`lib.rs:3123`, `3170`, `3867–3870`).
2. HUD `dock` means distance <= SAFE_RADIUS 240 (`lib.rs:71`, `3275`). Panel/start eligibility tests this HUD boolean, with no diagnostic flag exposed (`main.ts:1215–1233`). A QA-warped player can therefore be visibly at Haven and offered Invite.
3. Native `begin_co_op` additionally requires the 128-unit DOCK_RADIUS, a living occupied player body, and no arena/diagnostic/boss-QA/stress state (`co_op.rs:321–349`; `lib.rs:72`). A diagnostic warp into the dock deterministically meets the diagnostic rejection condition and returns `not_at_dock`. This is the correct progression-isolation guard.
4. Controller startup creates the signaling session first, then calls native `begin`. An unsuccessful native result is refused; no native-active state is retained. The current start catch maps this to `session_failed` and closes signaling (`controller.ts:350–418`). Batch handling discards the particular native error code (`controller.ts:268–294`). The panel has a truthful `not_at_dock` message, but `session_failed` uses the generic Connection stopped fallback (`panel.ts:46–60`, `230–235`).
5. Brief leave/end controls do not establish native hosting: the panel treats creating/joining/admitting/loading as active for exit controls (`panel.ts:178–184`, `242–252`). Controller assigns hosting only after successful native admission (`controller.ts:390–400`).

The source path explains how the observed QA-warped failure can occur without a JavaScript exception, network failure or host-frame failure. It is a supported explanation rather than proof that this was the particular failed run. The fresh unwarped success is consistent with it. No code change is recommended for this release; Root elected to retain the QA-specific Invite-unavailability issue. A future UX change could preserve a controlled native rejection reason or expose authoritative eligibility without weakening diagnostic isolation. Actual native error capture or a dedicated public warp->begin regression would establish run attribution more directly.
